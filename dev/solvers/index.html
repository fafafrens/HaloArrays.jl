Linear & implicit solves

A halo array can be the state vector of a matrix-free solve — an implicit ODE step, or a LinearProblem — without ever marshalling its interior to a flat Vector. The operator is applied through mul!, and convergence is judged by dot/norm, which HaloArrays defines as global reductions — so the same solve is automatically correct across MPI ranks and threaded tiles.

These solvers live in package extensions: the coordinate-free HaloCG/HaloMINRES/HaloBiCGStab/HaloGMRES activate when LinearSolve is loaded, and HaloKrylovKit when LinearSolve and KrylovKit are:

using HaloArrays, LinearSolve            # HaloCG, HaloMINRES, HaloBiCGStab, HaloGMRES
using KrylovKit                          # + HaloKrylovKit(:gmres | :cg | :bicgstab)

Which solver to use

Both families take a halo array of any dimensionality, or a field collection, as the unknown; both are matrix-free and MPI-collective.

solverfornotes

HaloKrylovKit`(:gmres:cg:bicgstab)`

LinearSolve's stock KrylovJL_* (Krylov.jl) and SimpleGMRES are not supported: they model the unknown as a flat AbstractVector, which a geometry-carrying halo array is not.

Implicit ODEs (Jacobian-free Newton–Krylov)

To integrate a stiff problem with the halo array as the SciML state, pass an iterative linsolve together with concrete_jac = false:

using OrdinaryDiffEq
solve(prob, FBDF(linsolve = HaloGMRES(),             concrete_jac = false))
solve(prob, FBDF(linsolve = HaloKrylovKit(:gmres),   concrete_jac = false))   # needs KrylovKit

An N-D or multi-field state passes through untouched: vec is the identity on any halo array (single array or field collection), so the integrator's internal flattening around its matrix-free W operator never wraps the state in a ReshapedArray, and rhs! keeps seeing its named fields.

To supply your own Jacobian-vector product instead of the automatic one, pass a matrix-free operator as jac_prototype (the jvp keyword of ODEFunction is not consulted on this path):

using LinearSolve.SciMLOperators: FunctionOperator
jvp!(Jv, v, u, p, t) = ...            # Jv .= J(u) * v; call synchronize_halo!(v) as rhs! does on u
J = FunctionOperator(jvp!, similar(u0), similar(u0); u = u0, p = p, t = 0.0, isinplace = true)
prob = ODEProblem(ODEFunction{true}(rhs!; jac_prototype = J), u0, tspan, p)

The integrator keeps u, p, t in the operator up to date at every Newton iterate, and the halo array (or collection) reaches jvp! unflattened. This replaces the rhs! evaluations the automatic JVP would make.

This works on distributed states too: OrdinaryDiffEq automatically wraps the iterative solver with error-weight preconditioners (Diagonal(weight) where weight is a halo array), and HaloArrays supplies elementwise mul!/ldiv! methods for them, so the whole implicit solve — Newton, GMRES, preconditioning, and the convergence-controlling norm/dot reductions — stays collective and correct across MPI ranks.

You must select an iterative linsolve

With the default linsolve (a factorization), the integrator builds a dense Jacobian matrix — which can't be formed column-by-column from a halo-array state, and errors. Only an iterative linsolve switches the integrator to the matrix-free (Jacobian-vector-product) path. This is what makes the halo array usable as the implicit state.

The Newton solve then just works: it is composed entirely of the RHS, the vector-space ops, and this linear solve — and its convergence norm is global, so every MPI rank makes the same accept/converge decision (no deadlock). See examples/finite_volume/stiff_reaction_diffusion_implicit_1d.jl and its _mpi_1d companion.

A LinearProblem directly

A = FunctionOperator(neg_laplacian!, similar(b), similar(b); islinear = true, ...)
sol = solve(LinearProblem(A, b; u0 = zero(b)), HaloCG())
Pass `u0` explicitly

For a LinearProblem, give u0 (e.g. zero(b)). LinearSolve's default initial guess flattens b to a 1-D vector of length size(A, 2), which a geometry-carrying halo array can't be.

See examples/poisson/operator.jl for a 2-D Dirichlet Poisson solved this way. Its poisson/mpi.jl companion applies the same matrix-free stencil with hand-written coordinate-free Krylov solvers across MPI ranks. For repeated LinearProblem solves, examples/schrodinger/crank_nicolson_2d.jl reuses one LinearSolve cache and one HaloGMRES workspace across every Crank–Nicolson time step.

Without LinearSolve: HaloArrays.Krylov

The algorithms behind the Halo* solvers are plain functions in the package, with an explicit workspace and no LinearSolve dependency:

using HaloArrays, HaloArrays.Krylov
ws = CGWorkspace(b)                                   # allocated once, reused
r  = cg!(x, A, b, ws; Pl = nothing, abstol = 0.0, reltol = 1e-8, maxiter = 200)
r.converged, r.iters, r.residual

A is anything with mul!, a preconditioner anything with ldiv!, and x is overwritten in place. The same kernels run on a Vector, which is how their edge cases are tested.

HaloArrays.Krylov — Module
HaloArrays.Krylov

Matrix-free Krylov solvers that touch the unknown only through similar, copyto!, broadcasting, dot, norm, mul! and ldiv!. They therefore run on a halo array of any dimensionality, on a field collection, or on a plain Vector, and stay correct under MPI, where dot/norm on halo arrays are global reductions and everything else is local.

cg!(x, A, b, ws::CGWorkspace;             Pl = nothing,               abstol, reltol, maxiter)
minres!(x, A, b, ws::MINRESWorkspace;                                 abstol, reltol, maxiter)
bicgstab!(x, A, b, ws::BiCGStabWorkspace; Pl = nothing, Pr = nothing, abstol, reltol, maxiter)
gmres!(x, A, b, ws::GMRESWorkspace;       Pl = nothing, Pr = nothing, abstol, reltol, maxiter)
fgmres!(x, A, b, ws::FGMRESWorkspace;     Pl = nothing, Pr = nothing, abstol, reltol, maxiter)

x holds the initial guess and is overwritten with the solution. A is anything with mul!(y, A, v). A preconditioner is anything with ldiv!(z, M, v) and ldiv!(M, v); nothing means none, and the solved system is Pl⁻¹ A Pr⁻¹ y = Pl⁻¹ b, x = Pr⁻¹ y. The workspace is allocated once from b and reused across solves. Each solver returns a Result; it stops when its residual measure falls below max(abstol, reltol * ‖b‖), with ‖b‖ taken in the same norm it monitors.

With LinearSolve loaded the same kernels are the HaloCG(), HaloMINRES(), HaloBiCGStab(), HaloGMRES() and HaloFGMRES() algorithms.

HaloArrays.Krylov.cg! — Function
cg!(x, A, b, ws::CGWorkspace; Pl = nothing, abstol, reltol, maxiter) -> Result

Preconditioned conjugate gradient (Saad, Iterative Methods for Sparse Linear Systems, Alg. 9.1) for A and Pl symmetric/Hermitian positive-definite. Left preconditioning in the Pl-inner product; the monitored residual is √⟨r, Pl⁻¹r⟩, which is ‖b - Ax‖ without a preconditioner. One operator product, two inner products and three vector updates per iteration.

source
HaloArrays.Krylov.minres! — Function
minres!(x, A, b, ws::MINRESWorkspace; abstol, reltol, maxiter) -> Result

MINRES (Paige & Saunders 1975) for symmetric/Hermitian A, indefinite allowed. Lanczos three-term recurrence plus a QR factorisation of the tridiagonal by Givens rotations, so the residual norm ‖b - Ax‖ is known without forming the residual. No preconditioning: that needs an SPD preconditioner and the preconditioned Lanczos process. One operator product, one inner product and one norm per iteration.

source
HaloArrays.Krylov.bicgstab! — Function
bicgstab!(x, A, b, ws::BiCGStabWorkspace; Pl = nothing, Pr = nothing, abstol, reltol, maxiter) -> Result

BiCGStab (van der Vorst 1992; Saad Alg. 7.7) for general square A, with split preconditioning Pl⁻¹ A Pr⁻¹. Directions are right-preconditioned before each operator product (p̂ = Pr⁻¹p, ŝ = Pr⁻¹s) and the solution is updated with them; products are left-preconditioned in place, so the monitored residual is Pl⁻¹(b - Ax), the true residual when Pl is nothing. Two operator products and four inner products per iteration.

source
HaloArrays.Krylov.gmres! — Function
gmres!(x, A, b, ws::GMRESWorkspace; Pl = nothing, Pr = nothing, abstol, reltol, maxiter) -> Result

Restarted GMRES (Saad & Schultz 1986; Saad Alg. 6.11) for general square A: Arnoldi with modified Gram–Schmidt on Pl⁻¹ A Pr⁻¹, Givens QR of the Hessenberg matrix, a restart every restart steps with the true residual recomputed, and maxiter honoured exactly. The monitored residual is Pl⁻¹(b - Ax), the true residual when Pl is nothing. The correction Σ yᵢ vᵢ is mapped back through Pr⁻¹ once per cycle, which assumes Pr is one fixed linear operator; for a preconditioner that changes between steps use fgmres!.

source
HaloArrays.Krylov.fgmres! — Function
fgmres!(x, A, b, ws::FGMRESWorkspace; Pl = nothing, Pr = nothing, abstol, reltol, maxiter) -> Result

Flexible GMRES (Saad 1993): as gmres!, but every preconditioned direction zⱼ = Prⱼ⁻¹ vⱼ is kept and the cycle update is x += Σ yᵢ zᵢ, so Pr may differ at every step — a nested iterative solve with a few iterations, smoother sweeps, a multigrid cycle. Pl is applied as in GMRES and must be one fixed linear operator, since it defines the norm being minimised; the monitored residual is Pl⁻¹(b - Ax), the true residual when Pl is nothing.
